## Technical decisions

- **Keep Unity Rigidbody + 60 Hz fixed step, URP, Input System, and current IMGUI menus** for this release. Gravity, bounded grip/roll/braking, contact probes, and camera already exist. Replace the UI or physics stack only after an observed defect warrants it. Keep Input Handling = Both while IMGUI and Input System coexist. No backend, multiplayer, paid service, DOTS, or framework migration.
- **Keep current ownership:** `LabRider` owns physical state/contact and samples `SnowSurfaceMap`; `MountainRun` owns run phase, finish and retry; `TrickScore` owns score rules; `LocalRunStore` owns file persistence; `MountainReplay`/`RunRecording` own bounded snapshot replay; HUD, camera, audio and spray read state. Editor builders remain in `Assets/EchoMountain/Editor`; runtime and PlayMode tests have separate assemblies. Add a tiny pure rule/config type only when a second difficulty or obstacle outcome requires it. Avoid a broad rewrite.
- **SOLID where useful:** single responsibility for physics, session, score and persistence; extend behavior through preset data or a surface map without branching through UI; keep pure rule functions independent of scene objects. Interface segregation/dependency inversion are justified only at a real boundary (for example, a replaceable save adapter), not for each MonoBehaviour. Composition with serialized references is sufficient now.
- **Patterns:** existing state machine (`MountainPhase`, rider support/recovery), data-driven strategy via surface coefficients and proposed difficulty presets, and snapshot replay are adequate. Do not add service locators, event buses, or factories for a one-scene MVP. A new ScriptableObject is optional if preset tuning is truly shared by scenes; two immutable definitions in code are simpler initially.
- **Quality gate:** add a small repository `.editorconfig` for whitespace, naming and common C# diagnostics; enable Unity-compatible Roslyn/.NET analyzers only after checking Unity 6000.3 support and baseline noise. Treat compiler errors and new warnings in touched code as failures; run Unity compile, focused test, full PlayMode regression, and Windows build at slice gates. Keep formatting of untouched generated/Unity YAML out of scope. Review allocations in `FixedUpdate` and `OnGUI` with the Unity Profiler before optimization. No lint success is claimed today; no `.editorconfig` or analyzer configuration was found.

## Agile delivery and acceptance

**Theme: Find your line. Ride it better.** Initiative A is a complete, trustworthy descent; B is readable surface and difficulty choice; C is Windows release confidence. Each epic below is a vertical slice with a player-visible story, not a subsystem rewrite.

| Priority / initiative / epic | User story | Measurable acceptance and gate |
| --- | --- | --- |
| 0 — A / close existing build gate | As a player I can start, finish and retry the corrected build. | On a fresh Windows launch, mouse and keyboard operate every primary menu; Pine finishes and Retry restarts at 0% with a reset timer; no player exceptions. Confirm save survives process restart. Record exact build hash/log. |
| 1 — B / visible surfaces | As a rider I can read packed, powder and ice before crossing them and feel the difference. | One owned course variant has aligned visual patches and map bounds; packed baseline unchanged; first supported tick after a boundary uses the new kind; airborne force unchanged; both lines finish/retry. Record version isolation passes; manual Windows pass identifies each zone without debug overlay. |
| 2 — A / fair obstacle/crash | As a rider I can avoid a visible obstacle and recover after striking it. | One obstacle collider matches the visible mesh, has a safe bypass on both lines, produces one crash outcome on a controlled hit, and Retry restores position, motion, pending score and timer. No false crash on normal course traversal. |
| 3 — B / difficulty choice | As a new or experienced rider I can choose a clear assist preset. | Two named configurations with specified steering/brake/landing values, shown before drop-in; same input fixture yields distinguishable bounded response; records/replays compare only matching preset/rules IDs; Retry preserves choice. Avoid claiming a wider progression system. |
| 4 — C / Windows MVP gate | As a player I can finish a comfortable run without setup. | Fresh build passes both lines, obstacle avoidance/hit, crash/retry, finish, pause, HUD and menu; physical keyboard tested; controller marked tested only if available. Review 1080p/60 FPS target with measured frame times and document hardware and limitations. |

The first implementation slice is **priority 1**, after the short priority 0 acceptance check. `SnowSurfaceMap` already resolves half-open world X/Z rectangles by priority (first serialized zone wins ties), and `LabRider` applies packed/powder/ice grip, rolling resistance and braking only when supported. Existing `SurfaceResponseTests` cover classifier, flat motion, braking, flight and reset. No Glacier Pass scene currently assigns a surface map, so course zones and their appearance are not delivered.

Minimum slice: inspect reachable points on both authored lines; generate a separate owned `GlacierPassSurfaces` scene with a few high-contrast powder/ice patches and matching `SnowSurfaceZone` rectangles, refusing to overwrite either scene; assign the map to the rider; add a brief surface label (and only simple audio/spray variation if needed for recognition). Keep ground collision and landing/scoring rules unchanged. Choose boundaries from the actual mesh and rider trajectory, not the example coordinates in the research blueprint. Before admitting altered runs into records, increment the course/rules compatibility version or use a separate course ID, and verify old saves remain readable without mixing record rankings. Replay is in-memory and stores course/rules/assist metadata; confirm metadata changes without changing its physics snapshot playback.

**Record compatibility decision (updated 2026-11-18):** the earlier key `(course="glacier-pass", courseVersion=1, rulesVersion=1, assist="balanced-lab-v1")` remains in `runs-v1.json`. This handling/landing slice uses `rulesVersion=2` and `runs-glacier-pass-c1-r2.json`; schema 1 still describes JSON shape, not riding physics. Keep the earlier file and backup byte-for-byte untouched, with no automatic best-time migration. A future surface variant should have its own course ID, `(course="glacier-pass-surfaces", courseVersion=1, rulesVersion=2, assist="balanced-lab-v1")`, and its own filename; bump rules again if its physics rules change beyond this slice. Show records only for the active exact key. If a later change alters route geometry, bump that route's course version; if it alters motion, scoring or assists, bump rules version or the actual assist ID. Do not bump schema unless serialization changes. `RunRecording` carries course/rules/assist metadata but playback is memory-only; it must capture the active key and never be presented as a persistent compatible ghost.

**Surface verification:** one pure Edit Mode test (or keep the existing `[Test]` in PlayMode until an Edit Mode assembly is worthwhile) for exact boundary/overlap behavior; one focused PlayMode transition test for packed→powder/ice, airborne crossing→first supported tick, reset, and unchanged landing award; existing full PlayMode suite once after integration; both authored-line finish/retry checks; then one Windows visual/feel pass crossing each zone with real input. Do not duplicate all coefficient fixtures in another test suite. Compare elapsed times with the recorded Pine 84.49 s / Summit 87.14 s simulated baseline as a diagnostic, not a hard acceptance threshold. Manual review checks patch readability before contact, clear traction change, HUD/audio timing, camera, and no invisible transition. Record exact commands, XML, build result and observations in `docs/QA.md`.

## Test economy and release constraints

- **Edit Mode:** pure classifier, difficulty validation, save comparability and score rules only; create an Edit Mode assembly when pure tests justify it. **Play Mode:** Rigidbody/contact, scene wiring, obstacle collision, transitions, reset and finish. **Manual Windows:** controls, visual readability, camera, sound, perceived traction, UI and performance. Use focused tests during a slice and a single full regression at its gate; avoid duplicating the same rule in all three layers.
- **Research site:** the supplied GitHub Pages reference is a separate research artifact. Its URL could not be fetched in this audit, so its live content is not asserted; use the checked-in `agent-context/01-GAME-IDEAS.md` for the surface blueprint. GitHub Pages is suitable for static research notes/screenshots, with no game backend. Do not publish the Unity project or player there by default. An optional Web build needs the Web module, build size/performance/input testing and a hosting trial: Unity 6.3 requires correct compression headers or decompression fallback, and GitHub Pages provides static hosting with a 1 GB published-site limit and soft bandwidth limits. Windows remains the acceptance target.
- **AI context:** start each slice from `AGENTS.md`, this plan, latest `STATUS`/`HANDOFF` and relevant `QA` section; inspect only touched source/tests. Keep a short decision, exact command/result, commit and next action at each checkpoint. Preserve `.meta` GUIDs, scene assets and unrelated work; use a separate QA checkout if the project is open, never force a lock. Update `PLANS.md` only when milestone scope or completion actually changes.
